# 电信客户流失分析与用户排序

> 面向数据挖掘实习的端到端分析项目：从客户分群与统计描述出发，比较分类模型，并在固定触达容量下评估客户排序策略。

## 项目概览

本项目基于公开的 Telco Customer Churn
数据，分析合同类型、在网时长和月费分组与历史客户流失之间的关系，并比较逻辑回归、随机森林在固定联系名额下的排序表现。

项目将数据处理、统计分群、机器学习评估和结果展示串成一条可复现流程：

-   **数据处理：** 使用 Pandas 检查字段、处理数值缺失并进行分层切分。
-   **统计分析：** 使用 SQLite
    对合同类型、在网时长和月费分组进行客户分群统计。
-   **模型评估：** 使用 scikit-learn
    Pipeline、五折交叉验证和独立测试集评估模型。
-   **业务排序：** 在相同的 Top-K
    联系容量下比较模型排序、简单规则和随机基线。
-   **结果展示：** 使用中文 Streamlit
    看板查看数据概览、分群、模型验证、触达排序和 AI 辅助解读。
-   **AI 辅助解读：** 将模型排序证据整理为可读摘要；AI
    不参与训练、打分或名单选择。

> **评估边界：**
> 本项目所有结果均来自公开数据上的离线实验。项目衡量的是对历史流失标签的识别与排序能力，不代表真实挽留效果，也不构成因果结论。

## 实验结果

以下结果来自已保存运行 `outputs/project_v1/` 中的 `metrics.json` 和
`policy_metrics.csv`。该目录中的运行产物默认不纳入版本控制；重新运行时，依赖版本变化可能造成数值差异。

### 1. 模型比较

实验包含 7,043 名客户。按流失标签分层划分为 5,634 条训练样本和 1,409
条测试样本，随机种子为 `42`。模型依据训练集五折交叉验证的平均 AP 选择。

-----------------------------------------------------------------------
  模型        五折 AP 均值 ±      测试集 AP 测试集 ROC-AUC      测试集 F1
                      标准差
----------- -------------- -------------- -------------- --------------
  逻辑回归          0.6614 ±         0.6334         0.8419         0.6040
                      0.0218

  随机森林          0.6504 ±         0.6399         0.8374         0.5714
                      0.0230
  -----------------------------------------------------------------------

**选择逻辑回归作为主模型。** 选择依据是训练集五折交叉验证 AP
均值，而不是测试集结果。虽然随机森林测试集 AP
略高，但不据此事后更换模型。F1 使用固定分类阈值 `0.5`；AP
指平均精确率。表中的标准差反映交叉验证各折之间的波动，不是置信区间。

### 2. 固定触达容量下的排序比较

测试集共有 374 名历史流失客户。将联系名额固定为排名前 140
人，即测试集人数的 10% 向下取整：

  排序方式           命中历史流失人数   Precision@140   Recall@140   Lift@140
---------------- ------------------ --------------- ------------ ----------
  逻辑回归                        104          74.29%       27.81%       2.80
  随机森林                        108          77.14%       28.88%       2.91
  短在网时长规则                   87          62.14%       23.26%       2.34
  随机选择的期望                37.16          26.54%        9.94%       1.00

-   **Precision@K：** 入选客户中历史流失客户所占比例。
-   **Recall@K：** 入选名单覆盖的全部历史流失客户比例。
-   **Lift@K：** 入选名单中的流失比例与测试集整体流失比例之比。
-   **随机基线：** 使用数学期望，因此命中人数可以是小数。

这组结果展示了固定联系容量下的离线排序差异。随机森林在该测试集的 Top-140
指标略高，但主模型仍按预先定义的训练集交叉验证规则选择，避免根据测试集反向挑选模型。

## 快速开始

### 环境要求

-   Python 3.10 或更新版本
-   项目根目录下可访问的公开数据 CSV
-   如需远程 AI 解读，再配置兼容接口；否则可使用离线模板

以下命令均在项目根目录执行。

### 1. 安装依赖

``` bash
python -m pip install -r requirements.txt
```

### 2. 准备数据

从 [Kaggle Telco Customer
Churn](https://www.kaggle.com/datasets/blastchar/telco-customer-churn)
下载 `WA_Fn-UseC_-Telco-Customer-Churn.csv`，放入 `data/` 目录。

程序使用原始字段，其中 `customerID` 必须非空且唯一，`Churn` 必须为 `Yes`
或 `No`。原始 CSV 不纳入版本控制。

### 3. 训练模型并生成报告

``` bash
python run_project.py --data data/WA_Fn-UseC_-Telco-Customer-Churn.csv --output outputs/project_v1 --test-size 0.2 --random-state 42
```

运行完成后，`outputs/project_v1/`
会生成指标报告、分群统计、排序结果和评估图表。具体文件用途见[项目结构与输出](#项目结构与输出)。

`--output` 必须位于项目目录内，且目标目录不存在或为空。重复运行时请使用
`outputs/project_v2` 等新目录，避免覆盖已有实验结果。若 CSV
不存在，请先下载数据。

核心实现位于 `churn_pipeline.py`，推荐通过 `run_project.py`
启动完整流程。

### 4. 启动看板

``` bash
python -m streamlit run dashboard.py
```

看板会自动列出 `outputs/`
中的完整报告，默认打开最近生成的一份；可以在页面"分析报告"中切换，不会重新训练模型。相对报告路径均以项目目录为基准。

如需固定查看某次运行：

``` bash
python -m streamlit run dashboard.py -- --output outputs/project_v1
```

已有完整报告可直接查看，无需重训。旧版输出可能只有模型指标和图片，缺少分群或策略表；看板会提示并展示可用的完整报告，不会将旧模型指标与新分群表拼接。若没有完整报告，页面会提示生成命令。

## AI 风险解读

看板的"AI风险解读"页只针对训练集五折 AP 选出的主模型所生成的固定 10%
优先名单，提供辅助说明。

工作边界如下：

-   统计模型负责风险排序。
-   AI 读取经过白名单筛选的客户特征、排序分数和训练集分群证据。
-   测试集真实流失标签不会进入 AI 上下文。
-   AI 不会修改模型分数、阈值或客户名单。
-   AI 输出是辅助解释，不作为因果结论或自动运营决策。

### 离线模式

不配置远程服务时，页面使用确定性的离线模板。项目无需本地模型、额外显存或网络调用即可演示。

### 配置 OpenAI 兼容接口（可选）

在项目根目录复制 `.env.example` 为 `.env`，并填写服务地址、模型名称和
API 密钥：

``` powershell
Copy-Item .env.example .env
$env:CHURN_AI_BASE_URL = "https://your-compatible-endpoint/v1"
$env:CHURN_AI_MODEL = "your-model-name"
$env:CHURN_AI_API_KEY = "your-api-key"
```

也可以直接将这三个值写入 `.env`。项目启动时会自动加载
`.env`，系统环境变量优先级更高。修改配置后需要重启 Streamlit。

-   API 密钥只从环境变量或 `.env` 读取，不应提交到版本控制。
-   远程接口未配置、超时或返回错误时，会回退到模板模式。
-   项目不接入 Ollama 等本地模型服务。

## 分析流程与评估设计

### 分析流程

![客户流失数据分析流程](docs/data-analysis-flow.png)

流程图对应一次完整运行：公开数据先经过字段和质量检查，SQLite 分群统计与模型训练并行使用训练数据；模型依据训练集五折 AP 选择后，再在固定测试集上做离线评估，并在同一联系容量下比较排序策略。最终结果由 Streamlit 看板展示，AI 只整理白名单字段和已有评估证据。

### 关键方法与设计理由

1.  **数据检查与分层切分：**
    检查客户编号、标签和数值字段，将空白数值转为缺失值，再按流失标签分层划分训练集与测试集。
2.  **训练集分群统计：** 运行
    [`sql/segment_analysis.sql`](sql/segment_analysis.sql)，统计合同类型、在网时长和月费分组的客户数、流失人数与比例；对少于
    30 人的组标记为小样本组。
3.  **避免预处理泄漏：** 使用 `ColumnTransformer` 和 `Pipeline`
    组织缺失值填补、数值标准化、类别独热编码与模型训练。预处理在每个训练折内拟合，避免交叉验证验证折信息泄漏。
4.  **模型选择：** 比较逻辑回归和随机森林，以训练集五折交叉验证 AP
    均值选择主模型，再报告两个模型的固定测试集指标。
5.  **容量一致的排序评估：** 在同一测试集和相同 10%
    联系名额下比较模型、短在网时长规则与随机期望。同分时按客户编号排序。
6.  **区分分类阈值与名额排序：** F1 和混淆矩阵使用固定分类阈值
    `0.5`；Top-K 排序直接按分数排名，不由该分类阈值决定。

特征重要性来自随机森林，用于描述该模型的变量使用情况，不能直接作为逻辑回归的解释结果。

## 使用限制与后续改进

### 当前限制

-   **缺少事件时间与观察窗口：**
    数据是客户快照，没有事件日期、预测时点、后续观察窗口和干预记录。因此不能将任务解释为严格的未来流失预测，也不能衡量挽留措施的真实收益。
-   **关联不等于因果：**
    合同类型、在网时长和月费分组之间的差异只描述历史关联，不能据此认定流失原因。
-   **公开数据基准并非盲测：**
    数据已用于项目开发和分析，固定测试集结果是可复现的公开数据基准，不是独立盲测。
-   **排序分数未经概率校准：**
    排序可用于离线比较，但不应将分数直接解释为准确的流失概率。
-   **模型结果可能随环境变化：**
    依赖版本和运行环境变化可能造成指标差异，简历中应以实际复现的结果为准。

### 可继续改进的方向

1.  使用带时间戳的客户行为数据构建明确的预测时点与未来观察窗口。
2.  对不同时间切分进行稳定性验证，并检查分群和排序效果是否随时间变化。
3.  在有真实干预记录时评估触达策略的增量收益，而不仅是历史流失标签命中率。
4.  对模型分数进行概率校准，并在明确的业务成本假设下评估阈值策略。

以上为后续方向，不代表当前版本已经实现。
